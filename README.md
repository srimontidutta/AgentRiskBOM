# AgentRiskBOM

*AgentRiskBOM: A Risk-Scoping Security Bill of Materials for Agentic AI Systems*

AgentRiskBOM is a security bill of materials for reviewing the delegated authority of tool-using AI agents. It extends the transparency provided by software and AI bills of materials with fields for runtime authority, including autonomy, tool permissions, memory, credential scope, approval gates, audit signals, inter-agent communication, and external action capability.

The approach is designed as an additive layer over SBOM, AI-BOM, and ML-BOM artifacts. Existing BOMs remain authoritative for software composition and model or training provenance, while AgentRiskBOM records the authority envelope assembled around a deployed agent.

## Overview

A conventional dependency inventory can show that an application includes a browser library, a model package, or a retrieval component. Security review of an agentic system also depends on the authority assembled around those components: whether an agent can invoke a shell, write files, communicate externally, retain sensitive memory, use broad credentials, or delegate work to another agent.

The paper describes the resulting transparency gap as **capability opacity**: the absence of a structured, reviewable account of what an agent can access, remember, change, delegate, and prove after the fact. AgentRiskBOM represents this information as a versioned artifact that can be reviewed before deployment and compared across releases.

## Reference schema

The [`schema/`](schema/) directory provides the machine-readable **AgentRiskBOM Reference Schema** in JSON Schema Draft 2020-12 and YAML. It represents the field structure and security relationships described in the paper and provides a common format for documenting the delegated authority of tool-using AI agents.

The schema covers agent identity, model context, prompt policy, tools, memory and data, orchestration, autonomy and authority, inter-agent relationships, audit evidence, and provenance. It also represents the fields used in the paper's risk-visibility analysis, including tool side effects and external endpoints, credential governance, approval requirements, RAG source trust, shared-memory and inter-agent relationships, logging, rollback evidence, and provenance signals.

Fields can be recorded as `unknown`, `not_applicable`, or `inherited`, allowing an AgentRiskBOM to reference an SBOM, AI-BOM, or ML-BOM where that artifact remains authoritative. This supports use of a common agent-security structure without requiring duplication of existing provenance information or disclosure of raw prompts, raw credentials, confidential documents, or proprietary execution traces.

Researchers and practitioners can use the reference schema to create AgentRiskBOM artifacts, compare agent authority across deployments or releases, develop compatible tooling, or extend the field model for additional deployment requirements. If you adopt, extend, or compare against the AgentRiskBOM schema, please cite the [AgentRiskBOM paper](https://arxiv.org/abs/2606.21877).

## What AgentRiskBOM records

| Layer | Security purpose |
| --- | --- |
| Agent identity | Owner, purpose, version, environment, business criticality |
| Model layer | Provider, model, version, hosting mode, linked AI/ML-BOM |
| Prompt-policy layer | Prompt hashes, change control, trusted boundaries, injection mitigations |
| Tool layer | Tool source, protocol, descriptor, permissions, side effects, risk tier |
| Memory-data layer | RAG sources, data classification, retention, vector store, retrieval logging |
| Orchestration layer | Framework, maximum steps, code/browser/network access, sandboxing |
| Autonomy-authority layer | Autonomy level, maximum tool tier, approval gates, emergency stop |
| Inter-agent layer | Delegation, shared memory, trust domains, identity propagation |
| Audit layer | Prompt, tool-call, retrieval, approval, and memory-write logs |
| Provenance | Generated by, commit hash, timestamp, signature, external BOM references |

Fields may be marked unknown, not applicable, or inherited from external artifacts. This allows the artifact to represent security-relevant deployment properties without requiring raw credentials, confidential documents, proprietary execution traces, or proprietary prompts.

See [`SPECIFICATION.md`](SPECIFICATION.md) for the field structure, design principles, review questions, scoring inputs, and lifecycle use described in the paper.

| Primary vs. secondary score correlation | Spearman rank correlation of 0.73 |
| Five-label categorical agreement | 46% |

The risk-scenario library is used as a coverage instrument: each category asks whether a BOM view contains the minimum fields needed for a reviewer to recognize that the modeled risk applies. The 100.0% result therefore concerns risk-category visibility across applicable corpus risks rather than live exploit success.

The authority-drift result concerns structured changes represented in the AgentRiskBOM schema, including tool additions, permission expansions, tier escalations, autonomy increases, memory-persistence increases, logging disablement, approval-gate removal, and model-provider changes. The scoring results support use of the score as a triage and change-review signal, while the 46% categorical agreement indicates that thresholds require human calibration.

The underlying tables are available in [`data/capability-matrix.csv`](data/capability-matrix.csv) and [`data/risk-categories.csv`](data/risk-categories.csv).

## Security-review questions

AgentRiskBOM is organized around six operational questions:

1. What can the agent do without a human?
2. What external systems can it affect?
3. What sensitive data can it see or remember?
4. Can risky changes be caught before deployment?
5. Could an incident be reconstructed?
6. Which controls should be required?

The representative fields for each question are available in [`data/security-review-questions.csv`](data/security-review-questions.csv).

## Agentic authority drift

**Agentic authority drift** is a deployment-level change in what an agent is able or permitted to do. Authority can change even when the base model, application code, or software dependency inventory appears unchanged.

Examples include a new write-capable tool, broader credential scope, persistent memory, external communication, reduced approval requirements, modified tool metadata, or a changed orchestration policy. Representing these properties in a versioned artifact makes such changes available for review before deployment.

## Use across the agent lifecycle

The paper identifies four points at which AgentRiskBOM can support security work:

- **Procurement:** record and review what an agent can access, remember, and change.
- **Pre-deployment review:** inspect approval, credential, memory, and logging properties before production use.
- **CI/CD:** compare versions for changes such as newly destructive tools, increased autonomy, disabled logging, expanded credential scope, or persistent memory over sensitive data.
- **Incident response:** use auditability fields to determine whether the evidence needed to reconstruct an action is available.

See [`docs/adoption-guide.md`](docs/adoption-guide.md) for a consolidated description of these uses.

## Relationship to SBOM, AI-BOM, and ML-BOM

AgentRiskBOM is designed as an agent-specific profile that sits alongside existing BOM classes. In the standardization path described in the paper, an SBOM remains the source of truth for packages, licenses, and vulnerability metadata, while an AI-BOM remains the source of truth for model and training provenance. The capability comparison treats ML-BOM as a complementary provenance artifact with native coverage for model metadata and dataset provenance.

AgentRiskBOM adds the operational layer needed to review tools, permissions, autonomy, memory, credentials, approval gates, inter-agent relationships, external actions, and audit evidence. See [`docs/mapping-to-sbom-aibom.md`](docs/mapping-to-sbom-aibom.md) for the full capability comparison.
